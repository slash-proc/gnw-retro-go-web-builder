# Library: the composed design

Five boards, from the pieces picked out of the ten-board set. All at 920.

| Board | Shows |
|---|---|
| `LibraryComposed` | The design at rest |
| `LibraryComposedSummary` | The same, dock expanded, carousel pushed up |
| `LibraryComposedOptions` | The same, options modal open on Cover art |
| `LibraryComposedOptionsSaves` | The same modal, Saves |
| `LibraryComposedOptionsCheats` | The same modal, Cheats |

Generated by `build-composed.py` on `shell.py`. The modal comes from `modal.py`, which is the
same definition the promoted `mockups/LibraryOptionsModal.dc.html` uses, so the modal and the
design it belongs to cannot drift apart. Extracting it changed that board by zero bytes.

## What was assembled

The approved upper part unchanged: console chip strip, games list at `span 5`, coverflow and its
info pane at `span 7`. Then the four changes asked for.

1. **`Favorites` immediately right of `All`**, count 12. It is a filter over the library rather
   than a system in it, and the strip already carries one of those, so it is the same chip in the
   same row. A star marks it as a filter. That is the conventional mark for this and introduces no
   new word.
2. **A search field.**
3. **`Additional options` at the foot of the info pane**, under the selected game's metadata. It
   is now the only way into the modal.
4. **`SummaryDock`'s dock**, without its top portion: the centred handle, the white panel, the
   six-category table with its trailing `Total`, the `Install` column, the meter and the bar.
   `Sync Library` is the approved board's red, not the green the frame boards borrowed.

**The dock's own `Additional options` disclosure is gone.** The trigger moved to the info pane,
and two controls opening one thing is the duplication this set existed to remove.

## The favourite star

**At the left edge of the row, before the system badge.** Three of the eleven visible rows are
set: the selected `Aerobiz Supersonic`, `Alex Kidd in Miracle World` and `Battle Kid`.

Left, because that is what makes it read as a toggle rather than a status. The right edge of the
row is the action pill, which is the row's one real action and the thing that says what will
happen on sync; anything put beside it joins that reading. At the left the stars line up into
their own column, which is where a per-row control belongs and how a checkbox column would sit.

**It is drawn in one place only.** It is not in the info pane beside the selected game's title,
although that pane describes exactly one game and could carry it. This design removed the dock's
`Additional options` disclosure on the grounds that two controls opening one thing is
duplication, and a second favourite toggle for the same game is the same mistake. The row is
where every game can be marked, so the row is where the control lives.

**Gold when set, a grey outline when not.** Not green: green is `installed`, two columns to the
right, and a favourite is not an install state. The gold is the chrome's own lip colour rather
than a new one, and the outline is the same polygon the `Favorites` chip uses.

### It does not cost a row

The row is **still 49**, which matters because that number is what makes eleven rows fit and the
list is the binding constraint on the whole design. A row's height is set by its tallest child:

```
star box       26      system badge   21      name   21
action pill    26      size           18
```

The star sits in a box of exactly the pill's 26px, so the tallest child is unchanged and the row
stays 49. A star with padding of its own would have made the row 52, and 11 rows would then need
604.5 against 607 with the header, leaving 2.5px of margin instead of 35.5 and no room for a
scrollbar. Horizontally the star costs 38px (26 plus the row gap), which leaves the name column
277px on a normal row and 257 on the selected one, against roughly 190 for the longest name
drawn, so nothing wraps and no row grows that way either.

**The chip count agrees with the rows.** `Favorites 12` against three set among the eleven
visible, out of 137. A subset the count can hold.

## Where the search field went, and why

**At the far right of the chip strip**, not among the chips.

The chips are one single-select scope, and they grow left to right as sources add consoles. A text
field joining that row would read as a ninth scope. Pushed to the right edge it is plainly a
different kind of control, the scope set stays one readable run, and `All` keeps `Favorites`
directly beside it, which is what was asked for.

This is the one element not named outright. It is drawn on the strength of the agreement that it
is missing, not slipped in.

## Does the collapsed dock fit 920

**Yes, with eleven rows.** `LibraryComposed` is drawn at a fixed 920 with overflow hidden rather
than growing to fit, because the app page is a fixed viewport and `.tabpane` is its only scroll
container. Heights are derived from the declared styles at the inherited line-height of 1.5:

```
chrome      56 header + 3 lip + 47 tab strip           = 106
chip strip  22 padding + 32 search field               =  54
dock        34 handle + 3 meter + 72 bar               = 109
body box    920 - 106 - 54 - 109                       = 651
body inner  651 - 20 top padding - 24 bottom padding   = 607
```

A game row is **49**: 11 padding, a 26px action pill, 11 padding, 1px hairline. The pill is the
tallest thing in the row, which is why a row is 49 and not the 43 a first pass estimates. With the
29.5px list header and 4px of card padding:

```
11 rows   571.5   fits, 35.5 to spare
12 rows   620.5   overflows by 13.5
```

So **eleven rows are drawn**; the twelfth and beyond are below the fold and reached by scrolling
the pane, which is what the real page does. The coverflow column needs 494.5 and has 112.5 to
spare, so **the list is the binding constraint, not the carousel**.

## What the expanded state does, and what it costs

Ruled by the owner after the first version of this board surfaced the problem:

> "that's fine, the bottom bar should be stuck to the bottom of the window and the summary
> opening up should push the carousel up once it bumps up to it. It should fill the space
> between the bottom of the carousel and bottom bar and opening the summary should fill that
> space until it reaches the bottom of the list/info box and then that makes the carousel move
> up."

`LibraryComposedSummary` draws that, **at 920**. An earlier version grew the board to 1290 to
show the whole table, which was the wrong answer: the page is a fixed viewport, so the expanded
state has to be shown inside one.

```
dock expanded   34 handle + 369 panel + 3 meter + 72 bar   = 478
body box        920 - 106 chrome - 54 chips - 478          = 282
body inner      282 - 20 - 24                              = 238
```

The two columns are anchored differently, and that difference is the behaviour.

**The list is anchored to the top and gets shorter.** At 238, with the 29.5 header and 4 of card
padding, four rows come to 228.5 and five to 277.5. So **four rows** are drawn where eleven fit at
rest, and the rest are below the fold exactly as row twelve is at rest.

**The carousel column is anchored to the bottom, against the dock.** It is 494.5 and cannot
shrink, so it rides up by 256.5 and its top goes above the body's top edge rather than under the
dock. That is the movement asked for: not covered, not clipped by the dock, moved.

The grid row is given an explicit height so an over-tall item overflows upward. Left to size
itself it would take the tallest item and spill past the bottom instead, which is the carousel
being clipped by the dock, and that is precisely what the ruling rules out.

### The cost, stated plainly

256.5 of the way up leaves **73.5 of the 330px coverflow in view**, and since the cards are 218
centred in that box, **about 17.5px of card**. So the ruling works and, at this table height, the
carousel is effectively gone while the summary is open.

That is not an argument against the ruling. It is the ruling applied to a 369px panel, and it is
a second decision that has not been made. If the carousel should stay legible with the summary
open, the panel is the thing to cap: at roughly 200px of panel the coverflow keeps about half its
height. Not drawn, because it was not asked for.

## Alignment: the highlight bleeds, it does not inset

The selected row carried `padding-left: 10px; padding-right: 10px` that no other row had, so its
star sat 10px right of the star column and its size and action pill 10px left of theirs. Being
the first row, it read as the top of the list being out of true with everything under it.

Now the row's **box** moves outward and its **content** does not:

```
margin-left: -10px; margin-right: -10px;
padding-left:  10px; padding-right:  10px;
```

The list card has 16px of side padding, so a 10px bleed stays 6px inside the card and collides
with neither its edge nor its 6px radius. The highlight still reads, and star, badge, name, size
and pill all line up down the list. The fix is horizontal only: the row is **still 49**, so eleven
rows still come to 571.5 against 607 at rest and four to 228.5 against 238 expanded.

### The same bug, swept for

One other instance, in the cheats presets. The checked box had no border and the unchecked one a
1px border, so under default content-box sizing they measured 15 and 17 across and every checked
label sat 2px left of every unchecked one. The checked box now carries a border of its own colour:
same outer size, same weight, no change to how either state reads.

Two things that differ between states and are **not** this bug, left alone: the active console
chip and the active modal tab are bolder than their siblings, which makes them wider and shifts
what follows them along the row. That is inherited from the approved board and there is no shared
column for them to fall out of, so it is a different question from a row whose content leaves the
grid.

**This divergence is worth knowing:** `docs/design/mockups/LibraryOptionsModal.dc.html`, the
promoted copy, still carries the original inset. It is in the approved set and not this
proposal's to edit, so it now differs from the `OptionsModal.dc.html` it was promoted from.

## All three tabs are drawn, and a claim I got wrong

My report on the original four boards said "Cover art, Saves and Cheats appear at full strength
on every board" and "cheats keeps both its presets and its manual entry everywhere". **That was
false.** Counted across the set:

| Board | Saves and Cheats content |
|---|---|
| `OptionsRail` | drawn |
| `OptionsInline` | drawn |
| `OptionsSheet` | not drawn, Cover art is the open section |
| `OptionsModal` | not drawn, Cover art is the open tab |

So it held for two of the four, and not for the one that was picked. Drawing one panel at a time
is how a tabbed modal works and is not the error; the error was saying otherwise, which left the
promise that all three sections survive at full strength unexamined in the design that was
chosen.

`LibraryComposedOptionsSaves` and `LibraryComposedOptionsCheats` close that. Content lifted from
`mockups/RomsOptions.dc.html`, where these sections are drawn today.

**Saves fits a tab comfortably.** The shipped `SRAM` / `Slot 0` / `Slot 1` picker with SRAM
selected, the written date, the download, and the preview in the same 300px column Cover art
uses with its arrows outside it. Nothing crowded, nothing dropped, and the modal frame does not
move between those two tabs.

**Cheats fits too, with room left, but the panel is shaped differently.** Cover art and Saves
each have an image on the right, so both use a `1fr 300px` body. Cheats has nothing to preview,
and stacking its four parts in one column would leave half the modal empty, so it is two equal
columns: what is set on the left, what you can add on the right.

**That the body grid is not the same on all three tabs is the thing to look at.** It is not a
problem in itself and a tabbed panel changing shape per tab is ordinary. It does mean the modal
cannot be built as one fixed two-column frame with swapped contents, which is worth knowing
before it is built.

## Which of these belongs in the approved set

**All three modal states, or none of them.** My reading, for the coordinator to act on.

The one already promoted, `mockups/LibraryOptionsModal.dc.html`, is the Cover art tab. On its own
it is the board that caused this: it reads as the modal, and the modal is three tabs. Promoting
Saves and Cheats beside it costs two boards in the index and answers the question the owner
actually asked, which was whether cheats survives as a real feature rather than a label.

The counter-argument is that the approved set is a reference, not a gallery, and three boards of
one modal is two more than it needs. If that wins, the honest alternative is to promote none of
them and leave all three here as the proposal, rather than keep the single Cover art board that
implies the other two were examined.

Two things the promoted copy needs either way, and neither is this proposal's to do: it still
carries the pre-fix selected-row inset, and it draws the modal over the old arrangement and the
old dock rather than the composed design.

## Still without a home

Two items from the keep-everything checklist are unresolved, in this design and across the whole
ten-board set. Neither is a regression introduced here; both were already homeless.

**BIOS rows.** Today they sit above the games in the same list, in their own `{#each}`, not
selectable, with a chip that opens the file picker. `RomManagementTab.svelte:2314` says out loud
that they must be excluded from the list's header count and from `Select all`. A thing that has to
be excluded from the list it is drawn in is not a list item, and this design does not draw them at
all. The modal is per-game and BIOS is per-system, so a BIOS tab there would be the wrong scope;
this needs its own answer.

**Unknown homebrew rows.** A bare on-device filename belonging to no active source's manifest,
drawn today as a row with `Remove`. Not drawn here either.

The `overview-v2` proposal solved both by making the console filter a rail and giving the
non-game things their own group in it. That is exactly the part of `overview-v2` this design does
not take, since the chip strip stays. So the question is open on its own terms rather than
answered by either proposal.

## Not verified

**Nothing here has been seen.** There is no headless browser in this environment. Every height
above is arithmetic over the declared styles, not a measurement of a rendered page, and the first
version of that arithmetic was wrong by 6px a row until the action pill was accounted for, which
is the kind of error that only a real render settles. Vertical rhythm, the star's optical
alignment in its chip, and the modal's centring are reasoned, not observed.

**Every number here is arithmetic, not a measurement.** The 49px row, the eleven-row and
four-row fits, the 256.5px the carousel rides up and the 17.5px of card left in view are all
derived from the declared styles. So is the alignment: the claim that the bleed keeps the
selected row's content on the same x positions as its neighbours follows from the box model, not
from seeing the two rows next to each other. If a real render disagrees, the eleven-row fit and
the star's 26px box are the first two things to recheck.

HTML nesting is parser-verified on all five boards, and the stars are counted in the emitted
markup: eleven per board at rest, three filled, and four with two filled on the expanded one.
Every visible string was extracted and checked: no em-dash, no interpunct, nothing invented
beyond `Favorites` and `Search`. The Saves and Cheats panels introduce no string of their own:
every label on them ships in `RomsOptions.dc.html` today.

**One correction to the approved upper part**, and it is a correction rather than a redesign. The
approved info pane writes the filename and size as a single string joined by a literal interpunct,
which `UI_VOICE.md` forbids and `apps/web/test/copy-dashes.mjs` fails the build on. The board
already draws a 3px dot between facts, so that dot now separates them and the character is gone.
Nothing else in the upper part changed.
